# エラーメール通知の設計案

設計日: 2026-09-18。ブランチ: `feat/error-email-report`。
今回は設計のみ。アプリ変更、認証変更、メール送信、Android反映は行っていない。

## 要件とメールの形式

1回の朝の実行で、最後まで解消しなかったエラーを1通にまとめる。
SDKやアプリのリトライで正常に復旧したエラーは含めない。
処理を中止するエラーと、一部機能を諦めて続行するエラーの両方を対象にする。

スクリーンショットはメールヘッダーの参考として扱う。家計簿システムの送信実装は未調査。
プロジェクト名に合わせ、以下を初期設定案とする（実際の個人アドレスは `.env` のみ）。

- From: `Your Name <your-account@gmail.com>`
- To: `Your Name+Ohayo-bot <your-account+ohayo-bot@gmail.com>`
- Reply-To: `Your Name <your-account@gmail.com>`
- 件名: `ohayo-bot エラーレポート（9/18）【処理中止】` または `【一部機能の失敗】`

本文は固定テンプレートで生成し、AIには送らない。テキストと簡潔なHTMLを用意する。
日時とタイムゾーン、実行ID、端末の区分（Mac / Android等）、実行結果、失敗した処理、
安全なエラー概要、再試行の結果、利用者が確認する項目を記載する。
再試行回数はアプリ側で把握できる値のみ記載する。SDK内部の回数を推測して表示しない。

例:

```text
ohayo-bot エラーレポート（9/18）
実行日時: 9/18 08:28 JST
実行結果: 音声再生まで完了。一部機能の失敗あり。

・電車の運行情報取得
  公式情報を取得できませんでした（通信タイムアウト）。
  原稿には「運行情報を確認できなかった」旨を伝える指示を渡しました。
  確認: 必要に応じて公式アプリをご確認ください。
```

## 通知対象

| 処理 | 通知する最終状態 | 通知しない状態 |
| --- | --- | --- |
| 設定・初期化 | 必須設定不足、設定値不正、依存関係の初期化失敗 | 正常な初期化 |
| 天気 | 通信・HTTP・必要データの検証失敗 | 正常な取得 |
| カレンダー | 当日・先の予定・祝日取得の最終失敗、認証失敗 | SDKの再試行で取得成功 |
| OpenAI原稿 | APIの最終失敗、空の原稿 | SDKの再試行で有効な原稿を取得 |
| TTS生成 | 生成候補がない、最終候補でも末尾欠落が残る | 再生成で末尾まで確認できる音声を取得 |
| TTS検査 | 選択した音声の検査失敗、時間不足で検査できなかった | 失敗した候補を捨て、検査済みの正常な候補を取得 |
| TTS補完 | 保存済みの締め挨拶で補完、補完失敗のまま再生 | 正常な全文音声を再生成 |
| 音声処理 | 末尾抽出や無音計測等が最終的に失敗したまま続行 | 別の方法・候補で同じ機能を正常に完了 |
| 電車情報 | 路線別の取得・解析失敗、情報が古い／未来のため確認不能 | 正常な取得（遅延・運休の取得成功も通知しない） |
| 音声再生 | コマンド失敗、再生状態確認失敗、完了待ちタイムアウト | 再生完了 |
| TTS診断保存 | 保存・古いデータ削除の失敗 | 正常に保存・削除 |

既存の処理継続・停止の判断は維持する。エラーがあるからといって、電車情報取得失敗で全体を止めたり、
カレンダー取得失敗を「予定なし」に変えたりしない。正常運行の取得や遅延・運休の情報はエラーではない。
リトライ中の警告ログをそのまま通知する方式にはしない。TTSは最終選択した候補の状態で判断する。

## 送信方法と設定

既存の `googleapis` でGmail APIの `users.messages.send` を利用する。
メール専用OAuthスコープは `https://www.googleapis.com/auth/gmail.send`。
カレンダー用のトークンは変更せず、メール専用トークンを `.secrets/` に保存する。
これによりカレンダーのトークン破損・権限不足をメール認証に引き継がない。
Google側・ネットワーク全体の障害は両方に影響し得る。

実装後の初回設定でGmail APIを有効化し、送信者のGoogleアカウントで専用認証を行う。
CLIに `pnpm auth:mail` を追加する想定。Macで取得したメールトークンはAndroidへ安全に反映する。
OAuthクライアントJSONは既存のものを再利用可能な構成とし、メール用のパス設定も独立させる。
メール認証の共通処理だけを小さく整理し、大規模なGoogle接続の抽象化は行わない。

設定案:

```dotenv
ERROR_REPORT_EMAIL_ENABLED=true
ERROR_REPORT_EMAIL_FROM=Your Name <your-account@gmail.com>
ERROR_REPORT_EMAIL_TO=Your Name+Ohayo-bot <your-account+ohayo-bot@gmail.com>
ERROR_REPORT_EMAIL_REPLY_TO=Your Name <your-account@gmail.com>
ERROR_REPORT_GOOGLE_CREDENTIALS_PATH=.secrets/google-oauth-client.json
ERROR_REPORT_GOOGLE_TOKEN_PATH=.secrets/google-mail-token.json
```

個人アドレス、認証ファイル、トークンはGitに追加しない。雛形は上のダミー値だけを記載する。
明示的に無効化した場合は従来どおり実行する。有効なのに設定や認証が不足している場合は
メール通知の設定不備をローカルに記録し、朝の処理自体は実行できるようにする。

根拠: [Gmailの送信API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send)、
[Gmail APIのスコープ](https://developers.google.com/workspace/gmail/api/auth/scopes?hl=ja)。

## 実装の配置と実行順序

- `src/domain`: 通知用の安全なエラー情報と、固定テンプレートの整形。
- `src/application`: 実行単位のレポート収集と、終了時の1回だけの送信。
- `src/infrastructure`: Gmail送信、送信用OAuth、通知失敗時のローカル保存。
- `src/bootstrap`: 通知設定の読み込みと依存関係の生成。
- `src/cli/index.ts`: 初期化を含む通常の朝の実行を囲み、終了時にレポートを確定する。

収集する情報は `stage`、`code`、`outcome`（中止／一部失敗）、安全な概要、発生時刻、
判明しているアプリ側の試行回数、対象日のような最小限の識別情報とする。
現状エラーを握りつぶしている電車情報、TTS検査・診断保存にも明示的な収集口を追加する。
TTS候補ごとの失敗情報を実行全体の最終失敗として即時記録しない。

朝の実行開始 → 各処理 → 再試行を含む最終結果の収集 → 再生完了または中止
→ エラーがあれば1通送信 → 元の成功／失敗を保持して終了。
通知は予約再生の前に待たせず、再生を終えてから送る。
並列処理は失敗時も各処理の結果が確定してからレポートを送信する。
既存の `Promise.all` の早期rejectにより後から発生するエラーが落ちないよう、
該当箇所は `Promise.allSettled` 相当で結果を回収し、中止の判断は維持する。

通知処理にも明示的なタイムアウトを設定する。MVPでは送信APIの自動再試行を無効にし、
送信結果不明時に重複メールを増やさない。送信失敗時は安全なレポートと送信失敗を
`~/.local/state/ohayo-bot/error-reports/` にディレクトリ700・ファイル600で保存する。
送信成功後は未送信ファイルを残さない。無期限の自動再送や通知失敗の通知ループは作らない。
通知失敗は元のエラーを上書きせず、朝の実行が成功していた場合も終了結果を変えない。
ローカル保存も失敗した場合は、安全な概要だけを標準エラー出力に残す。

## 情報の取り扱い

メールにはAPIキー、アクセストークン、更新トークン、HTTPヘッダー、APIのリクエスト／レスポンス全体、
カレンダーの予定内容、朝の原稿、文字起こし、音声ファイルを含めない。
SDKの例外やスタックトレースをそのままメールに載せず、段階とエラーコードから安全な概要を作る。
文字列のマスキングだけに頼らず、送信可能な項目を限定する。HTMLは必ずエスケープする。

## 範囲と制約

対象は通常の朝の実行（`--no-speech` を含む）。認証、サンプル、helpの操作には通知しない。
AIの呼び出し回数は増やさない。既存のリトライ回数・原稿生成・音声生成の動作も変更しない。
エラーのあった実行に、Gmail API呼び出しが1回追加される。

Node.jsが起動する前のCron・pnpm・ランナーの失敗、強制終了、OSの停止、Cronが起動しなかったケースは
アプリ内の通知では検知できない。既存のCron失敗ログは維持する。
これらまで通知するには独立した監視が必要であり、今回のMVPでは保証しない。
実行後の正常復旧はその実行のリトライによる復旧を指し、翌日の成功で前日のエラーは取り消さない。

## 実装後の検証

外部通信のないUTで、再試行成功時は送らない、最終失敗／部分失敗は1通、複数の並列エラーを集約する、
TTSの正常候補を選択した場合は過去候補の失敗を除外する、空原稿、初期化失敗、通知失敗時の元結果保持、
機密データを含めない、HTMLのエスケープ、通知が再生後に走ることを確認する。
`pnpm typecheck`、`pnpm build`、`pnpm test`、`git diff --check` を実施する。
実装・認証設定後、テスト通知の受信を確認し、必要ならAndroidへの反映と端末上の確認を別途行う。
